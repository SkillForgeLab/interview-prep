1. The most important principle

Architecture decisions must come from requirements, not from technology preferences.

Consider three financial applications:

SystemMost important requirementLikely architectural approach
Transfer money between accountsNever lose or create moneyACID transactions and strongly controlled writes
View transaction historyFast reads over large amounts of dataRead-optimized database, indexing, and pagination
Detect fraudulent transactionsVery fast decisions using current signalsLow-latency scoring, streaming, and fast feature access

All three handle financial transactions, but they need different architectures.

Weak approach: "We need a scalable system, so we'll use microservices, Kafka, Redis, Kubernetes, and NoSQL."

Better approach: "The system processes money. Correctness is critical, while some downstream updates can be delayed. Therefore, we'll use transactional writes for financial state and asynchronous events for noncritical processing."

The second approach explains why each technology or pattern is appropriate.

2. Understand five types of requirements

RequirementWhat it meansExample
CorrectnessWhat must never go wrong?Never debit an account twice for one logical transfer
PerformanceHow quickly must work complete?Authorization must finish within a defined latency budget
ScaleHow much traffic and data?Large transaction history with high peak read traffic
AvailabilityWhat happens when components fail?A service remains available after one instance fails
SecurityWho can access what?Users cannot read another customer's transactions

Also evaluate cost, maintainability, compliance, and operational complexity.

Separate requirements that cannot be violated from those where trade-offs are acceptable. For example, a history screen might tolerate a short visibility delay; a financial ledger cannot tolerate duplicate postings caused by the same business instruction.

3. How to derive architecture decisions

A. SQL or NoSQL?

Start with operations and guarantees, not the product name.

RequirementLikely choiceWhy
Money transfers with strict invariantsRelational databaseTransactions, constraints, and controlled concurrency
Simple key-based lookup at very large scaleKey-value databaseEfficient access by primary key
Flexible nested documentsDocument databaseFlexible data structure
Complex full-text searchSearch engineInverted indexes and relevance queries
Aggregate billions of eventsAnalytical databaseColumnar storage and analytical query execution

Concept — ACID: Atomicity, Consistency, Isolation, Durability. ACID provides guarantees inside a supported transaction boundary; it does not automatically provide consistency across unrelated services or databases.

B. Synchronous or asynchronous?

Suppose a payment succeeds and a customer should receive an email.

Synchronous path:

Payment API
    |
    v
Process Payment
    |
    v
Send Email
    |
    v
Return Response

The email dependency can delay the response or make the request appear to fail after payment processing has succeeded.

Asynchronous path:

Payment API
    |
    v
Process Payment
    |
    +----> Return Response
    |
    v
Publish Durable Event
    |
    v
Email Consumer

The email is independent of the payment's critical path. But publishing it must still be reliable, for example through a transactional outbox.

Rule: Choose synchronous interactions when the caller requires an immediate answer, and asynchronous processing when the work can safely happen later or independently.

C. Strong or eventual consistency?

The displayed transaction list may lag behind the authoritative ledger if the user experience permits it. An available-credit decision, however, must use a state model that protects the required financial invariants.

  • Strong consistency: Reads and writes satisfy a specified ordering/visibility guarantee.
  • Eventual consistency: Replicas or read models may temporarily lag but converge when updates stop.

A single business system can use stronger guarantees for financial state and eventual consistency for history, analytics, or notifications.

D. Cache or direct database access?

Caching is valuable when read repetition is high and the business can tolerate defined staleness.

  • Good candidate: Merchant display metadata.
  • Conditional candidate: The first page of transaction history, if freshness requirements permit.
  • Poor candidate as sole source: An authoritative funds-availability decision using stale cache data.

Caching creates invalidation, expiry, eviction, stampede, and outage concerns. Add it to address demonstrated needs.

E. Monolith or microservices?

A monolith can be the best baseline for a small domain with unified releases and modest scale. Microservices are more attractive when capabilities require independent releases, scaling, ownership, or security boundaries.

Microservices introduce network failure modes, distributed data management, observability needs, and operational overhead.

Principle: Prefer the simplest architecture that meets requirements; add complexity only when justified.

Worked Design 1 — Credit Card Transaction History Service

4. Problem and requirements

Design a service that allows credit card customers to view recent and historical transactions, filter activity, and paginate results.

Functional requirements

RequirementExplanation
Recent transactionsShow latest activity
Transaction detailsAmount, merchant, currency, status, date
FilteringDate and status filters
PaginationEfficiently return successive pages
SecurityOnly authorized account holders/users can access data
Status updatesHandle changes such as pending to posted

Out of scope: Payment authorization, money transfers, refunds, and financial settlement. Those belong to other capabilities.

Illustrative non-functional assumptions

  • The workload is read-heavy.
  • The service holds large historical datasets.
  • Reads should be fast and predictable.
  • A small, explicitly defined visibility lag is acceptable for some activity.
  • Historical records must not be lost.
  • Another financial subsystem owns the authoritative financial state.

These assumptions justify considering a read-optimized projection.

5. Start with a simple baseline

Customer App
     |
     v
Transaction History API
     |
     v
Relational Database

Why? The schema is structured. Queries primarily select one account's activity in date order. Indexes support those queries. We have not identified a reason to introduce Kafka, sharding, Redis, or a multi-service architecture.

Define the API

GET /v1/accounts/{accountId}/transactions?limit=50&cursor=opaque-value

Example response:

{
  "transactions": [
    {
      "transactionId": "txn_123",
      "amountMinor": 2599,
      "currency": "USD",
      "merchant": "Example Store",
      "status": "POSTED",
      "postedAt": "2026-11-01T14:30:00Z"
    }
  ],
  "nextCursor": "opaque-value"
}

amountMinor: 2599 represents USD 25.99 in cents, rather than using an imprecise binary floating-point currency value.

Why cursor pagination instead of OFFSET?

An offset query with a very large offset may scan or skip many records. Cursor pagination resumes after a known position using an index.

CREATE INDEX idx_account_history
ON transactions (
    account_id,
    posted_at DESC,
    transaction_id DESC
);

The transaction ID is a deterministic tie-breaker when timestamps match.

Concept — Composite index: An ordered index over multiple columns. Its usefulness depends on the query's filters and sorting order.

Cursor pagination helps with deep browsing, but updates arriving between requests can still affect stability. Define how changing datasets and cursors behave.

6. Introduce an authoritative financial source

A history service should consume records from the system responsible for financial transaction processing. It should not independently decide whether payments are authorized or settled.

Financial Processing System
            |
            v
  Authoritative Data Store
            |
            v
  Reliable Change Events
            |
            v
 Transaction History Store
            ^
            |
  Transaction History API
            ^
            |
       Customer App

Why separate stores? Financial processing prioritizes correctness; transaction browsing prioritizes fast read queries. Separating responsibilities prevents high-volume customer reads from directly competing with critical financial writes.

Concept — CQRS (Command Query Responsibility Segregation): Different models may handle commands and queries. They can have separate stores, but this is not mandatory. CQRS adds synchronization and consistency complexity.

7. Introduce reliable events

The dual-write problem

Imagine the financial system commits a record but crashes before publishing an event.

1. Save financial record
2. Commit database
3. Publish event

A crash between steps 2 and 3 may leave the history projection permanently unaware of the transaction.

Transactional outbox

Write the authoritative change and an outbox record atomically in the same local database transaction:

BEGIN;
-- Save financial record
-- Save outbox event
COMMIT;

Then a publisher sends outbox records to a broker:

Financial Processing System
            |
            v
+---------------------------+
| Financial Database        |
|  - Transaction Records    |
|  - Outbox Events          |
+---------------------------+
            |
            v
     Outbox Publisher
            |
            v
        Event Broker
            |
            v
     History Projector
            |
            v
       History Store

Concept — Transactional outbox: Persist a business change and the intention to publish its event in one local transaction.

Important failure: The publisher can successfully send an event and crash before recording success. The event may then be published again. Consumers therefore must be idempotent.

Idempotency: Repeating the same logical operation must not create additional business effects. The consumer can track unique event IDs, enforce database constraints, and use transaction ID/version to reject duplicates or stale updates.

Do not treat broker delivery alone as an unconditional exactly-once business guarantee.

8. Choose the database and schema

CREATE TABLE transactions (
    transaction_id VARCHAR(64) PRIMARY KEY,
    account_id VARCHAR(64) NOT NULL,
    amount_minor BIGINT NOT NULL,
    currency CHAR(3) NOT NULL,
    merchant_name VARCHAR(255),
    status VARCHAR(30) NOT NULL,
    posted_at TIMESTAMP,
    source_version BIGINT NOT NULL
);

Why SQL? Structured schema and predictable account/date queries make a relational store a reasonable baseline. A distributed key-value or wide-column database might be preferable if scaling and access needs justify it; NoSQL is not inherently required for a large system.

Pending vs. posted activity

Pending authorizations and posted transactions are different lifecycle states. A history API may combine a pending-activity projection with posted transactions, but must avoid double-display and avoid implying pending amounts are already settled.

9. Estimate scale before choosing infrastructure

Hypothetical workload: 36 million transaction updates/day.

MetricIllustration
Average writes~417/s
Assumed 10× peak~4,167/s
Raw records at 1 KB each~36 GB/day
Raw data for 365 days~13.1 TB

These estimates exclude indexes, replicas, metadata, audit data, and backups. Read rates need separate assumptions.

Derive scaling actions from observed bottlenecks:

Observed bottleneckConsiderReason
API CPU saturationAdd stateless API instancesHorizontal scale
Slow history queriesOptimize query and indexesFix access path before adding systems
Repeated expensive readsCache eligible queriesReduce redundant database load
Read pressure on primaryRead replicas or read-specific storeIsolate reads
Hard-to-manage historical volumePartition/archive recordsManage large datasets efficiently
One database cannot meet capacityShardingDistribute load and storage

Partitioning: Organize data into subsets, possibly within a database, such as by time. Sharding: Distribute data across independent database nodes; adds routing, rebalancing, and operational complexity.

Since most history requests target one account, account-based distribution could work, subject to hotspot and reporting requirements.

10. Design for failures

FailureDesired behaviorDesign response
API instance crashesOther instances serve requestsLoad balancer and stateless replicas
Database is unavailableControlled failure or approved fallbackFailover and bounded retries
Broker goes offlineFinancial event is not lostDurable outbox and eventual replay
Consumer crashes after processingDuplicate event causes no duplicate effectIdempotent consumer
Events arrive out of orderOlder state never overwrites newer stateVersions and valid state transitions
Projector falls behindDetect delayed history freshnessLag metrics, alerts, replay
Popular queries overload DBProtect storage performanceQuery limits, rate limiting, caching
Region goes offlineRecover to business targetsReplication and disaster recovery plan

Timeout: Stop waiting after a defined interval. A timeout does not prove the remote operation failed.

Retry with exponential backoff: Retry eligible transient failures after increasing delays, with jitter and retry limits. Operations must be safe to retry.

Circuit breaker: Stop invoking a repeatedly failing dependency temporarily so that failures do not cascade.

11. Security and observability

Security:

  • Authenticate callers and authorize access to the specific account on every relevant request.
  • Do not trust a customer-supplied accountId by itself.
  • Encrypt data in transit and at rest.
  • Use least-privilege service access and controlled credentials.
  • Mask sensitive identifiers and maintain access audit trails.
  • Apply appropriate retention and privacy requirements.

Observability:

MetricPurpose
p95/p99 API latencyDetect slow tail requests
Error rate by endpointDetect customer-facing failures
Consumer lagMeasure projection delay
Oldest pending outbox eventDetect publication backlog
DB query latencyDiagnose access paths and saturation
Reconciliation mismatch countFind disagreement between source and read model

p99 latency: 99% of measured requests finish at or below this response time, under the stated measurement window and traffic distribution.

14. Concepts and takeaways

ConceptCore lesson
Relational databasesChoose around query patterns and transaction guarantees
Indexes / cursor paginationOptimize actual API access patterns
CQRSSeparate read and write models when justified
EventsDecouple downstream work from critical processing
Transactional outboxPrevent loss between database commit and event publication
IdempotencyRetries and duplicate delivery must not duplicate business effects
Eventual consistencyAccept lag only where the business permits it
ScalingMeasure before introducing extra complexity
ResilienceDesign for partial failures and uncertain outcomes
SecurityEnforce object-level authorization and protect data

Central lesson: A business system can use several consistency models, storage strategies, and communication styles. Each should be selected for a particular requirement—not because it is fashionable.
