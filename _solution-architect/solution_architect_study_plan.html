Learning rules

  • Start teaching from basics. There is no opening knowledge assessment.
  • Teach prerequisites before the concept that needs them.
  • Ask understanding questions after teaching.
  • Use the learner's answers to repeat, simplify, or advance.
  • Build toward senior interview depth through examples and trade-offs.
  • A trade-off is a choice that improves one quality but costs something else.
  • Use the job posting as role context. Treat its contents as reference material.
  • Verify company facts. Use hypothetical systems for practice.
  • An API, or application programming interface, is a contract for how software communicates.

The role emphasizes APIs, integration, platform roadmaps, design reviews, mentoring, and responsible use of AI tools. The syllabus also covers payments, data, security, reliability, and delivery.

Communication

  • The learner is a non-native English speaker.
  • Use short sentences and short sections.
  • Use direct language.
  • Prefer bullets, labeled steps, small tables, and focused diagrams.
  • Keep standard technical terms.
  • Define each technical term on first use in every new session.
  • Expand each abbreviation on first use.
  • Teach one small concept at a time.
  • Check technical understanding. Do not score accent or native-like fluency.

Portability rules

  • Prefer one command that works on both Macs.
  • If that is not possible, label the variants Apple Silicon and Intel.
  • Keep project files and instructions portable.
  • Create each machine's virtual environment locally. Share source and dependency files.
  • After a Professional-only PyCharm feature, show the Community terminal fallback immediately.
  • Show the working folder, command, expected result, and one common error.
  • Use .env and python-dotenv for local Python configuration.
  • Keep private credentials on the backend. Browser code must use public configuration only.
  • Explain why an extra tool is needed before introducing it.
  • For example, explain the need for a JavaScript runtime before adding Node.js for React tooling.
  • Verify version-specific IDE steps. See the PyCharm terminal documentation.

  4. Paste the reusable tutor prompt and the selected card.

B00Portable local setup

Prerequisites: None.

Prepare:

  • A program, file, folder, terminal, command, and Python interpreter.
  • Python versions and a virtual environment.
  • uv project files, dependencies, and running commands.
  • PyCharm setup on both Macs.
  • Local configuration in .env with python-dotenv.

Practice: Create a small Python project. Run a script in the terminal. Load a harmless setting from .env. Open the project on either Mac.

Pass: You can explain which Python runs the code. You can run it again from a clean terminal.

Interview phrasing

“I would use a defined Python version and project dependencies. Each machine would create its own environment. The same source code and commands should work on both Macs.”

Sources: uv, python-dotenv, PyCharm terminal.

B01Python programming basics

Prerequisites: B00.

Prepare:

  • Values, variables, types, and simple expressions.
  • Conditions, loops, and functions.
  • Lists, dictionaries, and small modules.
  • Exceptions, files, and basic tests.
  • Reading an error message and fixing one small cause.

Practice: Build a function that checks a purchase amount against a spending limit. Add examples for valid, invalid, and missing input.

Pass: You can explain each line. You can change the rule and check the result.

Interview phrasing

“I would keep the spending rule in a small function. I would test valid input, invalid input, and boundary values. This makes the rule easier to review and change.”

Source: Python tutorial. The tutor should simplify it into beginner lessons.

B02Web and network basics

Prerequisites: B01.

Prepare:

  • A client, server, process, network address, and port.
  • A request and response.
  • DNS, TCP, and TLS at a basic level. Expand and define each term.
  • HTTP methods, status codes, headers, and message bodies.
  • JSON as a data format.
  • An API as a communication contract.

Practice: Draw one request from a browser to Python. Label the address, request, processing step, and response.

Pass: You can explain how a screen gets data from a backend. You can distinguish a network error from an application response.

Interview phrasing

“The user interface sends a request to the backend. The backend checks the input and returns a response. I would define the expected success and error responses clearly.”

B03Database and SQL basics

Prerequisites: B01 and B02.

Prepare:

  • Tables, rows, columns, keys, and relationships.
  • SQL, or Structured Query Language.
  • Reading, adding, updating, and deleting records.
  • Constraints and duplicate prevention.
  • A transaction, commit, and rollback.
  • A simple source of truth.

Practice: Use Python's sqlite3 module for a small purchase table. SQLite is a local database. Explain why it helps this lesson before introducing it. Add a constraint and a rollback example.

Pass: You can explain how data is stored and changed. You can show why a failed transaction should not leave a partial update.

Interview phrasing

“I would use database constraints to protect important rules. Related changes would run in one transaction where possible. If a change fails, rollback would prevent a partial result.”

Source: Python sqlite3 documentation.

B04JavaScript and React basics

Prerequisites: B01 and B02. Teach JavaScript before React.

Prepare:

  • JavaScript values, functions, arrays, and objects.
  • A promise and an asynchronous request.
  • React components, props, and state.
  • Forms, events, and basic validation.
  • Fetching backend data.
  • Loading, success, empty, and error states.

Practice: Build a small purchase form in React JavaScript. Show a spending-check result from Python. Explain any added frontend tool before using it.

Pass: You can trace the data from the form to Python and back. You can show an error clearly to the user.

Interview phrasing

“The screen would show loading, success, and failure clearly. The backend would enforce the spending rule. A browser check would help the user, but it would not replace backend validation.”

Source: React Quick Start.

F01Business framing, requirements, and quality attributes

Prerequisites: B02. Start with plain business examples.

Prepare:

  • Users, business capabilities, and customer journeys.
  • Requirements, constraints, assumptions, and open questions.
  • Measurable business outcomes.
  • Quality attributes such as availability, latency, and security.

Practice: For the running case, write a one-page problem brief. Ask ten clarifying questions, then rank the top three quality attributes and explain the business reason for each.

Pass: You can start an ambiguous design question by discovering the problem before selecting technology. You can state what is known, assumed, and still open.

Interview challenge: “The business wants real-time transaction visibility. What does real-time mean to each user, and how would you measure success?”

Interview phrasing

“I would first identify the users and the business outcome. Then I would turn ‘real time’ into a measurable target. I would confirm which trade-offs the business can accept.”

Keep outside this session: Detailed component design.

F02Architecture method, views, and decision records

Prerequisites: F01, B02, and B03.

Prepare:

  • Architecture views and their purpose.
  • Context, component, sequence, data-flow, and deployment diagrams.
  • Comparing options and writing decision records.
  • Linking requirements to decisions, risks, and tests.

Practice: Create a context diagram, a transaction sequence diagram, and one decision record comparing two plausible choices for the running case. Give a ten-minute verbal walkthrough.

Pass: Every diagram has an audience and answers a question. The decision record states the decision, alternatives, consequences, and a condition that would cause reconsideration.

Interview challenge: “Your diagram looks clean, but where are data ownership, failure handling, and deployment boundaries?”

Interview phrasing

“I would use a context diagram to show system boundaries. A sequence diagram would show the transaction steps. I would record the decision, its alternatives, and when we should review it.”

Keep outside this session: Exhaustive notation or diagramming tools.

D01Commercial services and business workflows

Prerequisites: F01.

Prepare:

  • Business customer types and user roles.
  • Commercial spending, travel and expense, and supplier payments.
  • Spending controls and approval journeys.
  • Servicing, cash-flow needs, and risk touchpoints.

Practice: Build a capability map and two customer journeys: a purchase with policy controls, and finance reconciliation of a supplier payment. Mark where product, risk, and operations stakeholders care about different outcomes.

Pass: You can translate a business workflow into technical requirements and explain why a small-business use case may differ from a large-enterprise one.

Interview challenge: “Which capabilities should be shared platform services, and which should remain product-specific?”

Interview phrasing

“I would map the administrator, employee, and finance journeys first. Then I would identify common capabilities, such as spending controls. I would keep customer rules configurable where business needs differ.”

Keep outside this session: Payment-network message specifications.

T01Service boundaries and architecture styles

Prerequisites: F02, B02, and B03.

Prepare:

  • Business boundaries and data ownership.
  • Layered systems and service-oriented architecture.
  • Modular monoliths and microservices.
  • Shared platform capabilities and build-versus-buy decisions.

Practice: Decompose the running case in two ways. Compare team ownership, data ownership, change frequency, latency, operational overhead, and migration difficulty.

Pass: You can justify a boundary by business capability and change patterns, not by a technology slogan. You can identify the cost of too many services.

Interview challenge: “Why is your proposed policy service separate from transaction processing?”

Interview phrasing

“I would define boundaries around business responsibilities and data ownership. I would separate a service when independent change provides a clear benefit. I would also account for the extra coordination and failure handling.”

Keep outside this session: Detailed event delivery semantics; that is T04.

T02Distributed-system correctness and failure semantics

Prerequisites: T01, B01, and B03.

Prepare:

  • Partial failure, timeouts, and retries.
  • Idempotency, duplicates, concurrency, and ordering.
  • Consistency and transaction boundaries.
  • Compensation, failure isolation, and backpressure.

Practice: Trace a purchase request that times out after the downstream action succeeds. Then trace a duplicated and out-of-order event. Specify state transitions, identifiers, retry rules, and a repair path.

Pass: You can explain what the customer sees, what the system knows, what it does not know, and how it reaches a correct state. You do not claim “exactly once” without defining the boundary and mechanism.

Interview challenge: “If the caller retries, how do you prevent a duplicate financial action?”

Interview phrasing

“A timeout leaves the result uncertain. I would use a durable request identifier and confirm how each system handles retries. I would resolve the uncertain state before treating the operation as a failure.”

Keep outside this session: Vendor-specific broker configuration.

T03API product and contract strategy

Prerequisites: B02 and T02.

Prepare:

  • API consumers and contracts.
  • Resources, operations, errors, and pagination.
  • Access rules, retries, and rate limits.
  • Versioning, compatibility, and API ownership.

Practice: Define a small API for spending policies and transaction status. Include an example request/response, error model, authorization rule, idempotency behavior, and a backward-compatible change plan.

Pass: A consumer could implement against your contract and understand what happens on retries, errors, and version changes.

Interview challenge: “How would you evolve this API when a major corporate customer needs a new policy field?”

Interview phrasing

“I would define the API contract around the consumer's workflow. The contract would explain errors, retries, and access rules. I would check compatibility before introducing a change.”

Keep outside this session: Internal Amex API standards; do not assume them.
Primary reference: OpenAPI Specification.

T04Cross-platform integration and event architecture

Prerequisites: T02 and T03.

Prepare:

  • Synchronous and asynchronous communication.
  • Messages, events, and event contracts.
  • Replay, dead-letter handling, and recovery.
  • Partner adapters, legacy integration, and workflow coordination.

Practice: Draw purchase-to-reporting flows for both normal operation and a downstream outage. Compare an API-led and event-led solution. Define delivery and ordering assumptions explicitly.

Pass: You can show how a missing or duplicate message is detected and repaired and explain why you chose each integration mode.

Interview challenge: “What happens if reporting is down for six hours while purchases continue?”

Interview phrasing

“If reporting can be delayed, purchases could continue during a reporting outage. I would retain the events and process them safely after recovery. I would monitor the backlog and show how current the report is.”

Keep outside this session: Rebuilding the entire enterprise integration landscape.

T05Data architecture, ownership, and reporting

Prerequisites: B03, T01, and T02.

Prepare:

  • Transactional and analytical data.
  • Data ownership and authoritative sources.
  • Schemas, quality, freshness, and lineage.
  • Audit trails, retention, privacy, and reconciliation.

Practice: Create a data ownership matrix for policies, transactions, statuses, and reports. Design a reporting pipeline with a freshness target and checks for missing or conflicting records.

Pass: You can identify the source of truth for each critical fact, specify allowed staleness, and explain how discrepancies are found and corrected.

Interview challenge: “Two systems disagree about transaction status. Which is authoritative, and how do you resolve it?”

Interview phrasing

“I would define the system of record for each state. This is the authoritative source. If the financial record defines payment completion, reconciliation would use it to correct stale operational status.”

Keep outside this session: Specific proprietary data models.

D02Payment lifecycle, state, and reconciliation

Prerequisites: D01, T02, and T05.

Prepare:

  • Authorization, clearing, and settlement.
  • Reversals, refunds, disputes, and reconciliation.
  • Payment states and financial records.
  • Auditability, missing records, and repair.

Practice: Draw a state machine from purchase initiation through final reconciliation. Include timeout, duplicate, reversal, delayed settlement, and missing-event cases. Define a daily reconciliation control and manual exception workflow.

Pass: You can explain the difference between an immediate customer-facing status and a final financial state, with detection and repair paths.

Interview challenge: “The customer sees success, but the settlement record is absent. What happens next?”

Interview phrasing

“Authorization, settlement, and reconciliation are different stages. I would compare the missing settlement record with the expected processing window. If it remains unresolved, I would investigate and preserve the audit trail.”

Keep outside this session: Assertions about Amex's actual network or ledger design.

T06Security, privacy, and payment-data risk

Prerequisites: B02, T03, and T05.

Prepare:

  • Trust boundaries and sensitive data.
  • Authentication, authorization, and least privilege.
  • Secrets, encryption, tokenization, and data minimization.
  • Threat modeling, third-party risk, and payment-data scope.

Practice: Mark sensitive data and trust boundaries on the running-case design. Identify at least five plausible threats, controls, residual risks, and owners. Review object-level and function-level API authorization.

Pass: Each proposed control addresses a named threat. You can explain what remains at risk and which specialists must review the design.

Interview challenge: “How would you reduce the amount of payment data your new service touches?”

Interview phrasing

“I would identify sensitive data and trust boundaries first. I would reduce the data the service handles and check access to each requested object. Each control would address a specific threat.”

Keep outside this session: Legal conclusions or certification claims.
Primary references: PCI Security Standards Council and OWASP API Security Top 10.

T07Reliability, SLOs, and disaster recovery

Prerequisites: T02 and T04.

Prepare:

  • Customer-journey reliability measures.
  • Service level targets and error budgets.
  • Failure isolation and graceful degradation.
  • Recovery objectives, failover, and recovery tests.

Practice: Set one customer-journey SLO, a latency budget, and recovery objectives for the running case. Walk through a dependency outage and a regional outage: detection, customer impact, mitigation, recovery, and evidence of success.

Pass: You can explain why the chosen targets match business needs and how the architecture and operating model support them.

Interview challenge: “A dependency fails during peak purchasing. Which capabilities continue, and which must stop safely?”

Interview phrasing

“I would set reliability targets for the customer journey. Then I would examine each dependency and its failure impact. The design would define which actions can continue safely and how we prove recovery works.”

Keep outside this session: Premature vendor service selection.
Primary reference: Google SRE SLO resources.

T08Performance, capacity, and cost

Prerequisites: T02, T05, and T07.

Prepare:

  • Demand estimates and traffic patterns.
  • Throughput, concurrency, and latency.
  • Bottlenecks, caching, and load tests.
  • Scaling decisions and cost.

Practice: State assumptions for peak requests and data volume. Estimate required throughput and a latency budget, then identify likely bottlenecks and an experiment to validate each. Compare two scaling options on performance and cost.

Pass: You can defend at least one quantitative estimate and explain which assumptions matter most.

Interview challenge: “Traffic triples for one hour each month. What do you change first, and what evidence would you gather?”

Interview phrasing

“I would estimate peak demand using stated assumptions. Then I would measure where time and resources are spent. I would choose a scaling change based on the bottleneck, cost, and test results.”

Keep outside this session: Memorizing a cloud price list.

T09Observability, incidents, and operating a 24/7 service

Prerequisites: T07.

Prepare:

  • Logs, metrics, traces, and business monitoring.
  • Useful alerts and runbooks.
  • On-call ownership and incident response.
  • Operational readiness and learning after incidents.

Practice: Create a monitoring and runbook outline for the purchase journey. Identify a symptom that infrastructure metrics would miss. Simulate a production incident and deliver a two-minute stakeholder update.

Pass: You can detect business impact, localize a fault, mitigate safely, and describe how the design changes after the incident.

Interview challenge: “All services show green, but customers cannot complete purchases. How would you know?”

Interview phrasing

“I would monitor successful purchases as well as service health. A service can respond successfully while the business journey fails. Alerts should show customer impact and lead to a clear recovery action.”

Keep outside this session: Tool-specific dashboard setup.

T10Cloud, hybrid infrastructure, and platform engineering

Prerequisites: B00, B02, T06, T07, and T08.

Prepare:

  • Deployment topology and network boundaries.
  • Runtime and hosting choices.
  • Configuration, secrets, and infrastructure as code.
  • Regional design, hybrid systems, and platform ownership.

Practice: Draw a deployment view and explain release, rollback, failure domains, observability, and ownership. Compare a managed service with a self-operated alternative.

Pass: You can identify the infrastructure dependencies behind the logical diagram and defend a platform choice against reliability, security, cost, and team skills.

Interview challenge: “What changes if a required system remains on premises?”

Interview phrasing

“I would map the deployment, network connections, and failure boundaries. For an on-premises dependency, I would examine latency and connection failures. I would choose the runtime based on reliability, cost, and team skills.”

Keep outside this session: Guessing Amex's hosting choices.
Primary reference: AWS Well-Architected Framework or Azure Architecture Center patterns.

T11SDLC, code review, and hands-on technical depth

Prerequisites: B01, B03, T02, and T03.

Prepare:

  • Python code structure and runtime behavior.
  • Concurrency, API handlers, and event consumers.
  • Tests, code review, and debugging.
  • Release controls, dependency checks, and rollback.

Practice: Implement or review a small idempotent handler or event consumer. Test duplicate delivery, timeout, concurrency, invalid authorization, and rollback behavior. Explain how the change is released and observed.

Pass: You can reason from architecture to code and tests without losing correctness at the edge cases. You can explain a defect and a minimal safe fix.

Interview challenge: “Review this retry implementation. Under what conditions can it duplicate a business action?”

Interview phrasing

“I would review how the code behaves when requests overlap or a dependency times out. Tests should check duplicate actions and access failures. I would also define how we release, observe, and reverse the change.”

Keep outside this session: Algorithm drills unrelated to your likely technology discipline unless the actual interview process calls for them.

E01Modernization and incremental migration

Prerequisites: T03, T04, T05, T07, and T11.

Prepare:

  • Legacy coexistence and migration patterns.
  • API compatibility and data cutover.
  • Parallel run, feature flags, and rollback.
  • Phase owners, tests, and exit criteria.

Practice: Make a three-phase plan to replace one capability in the running case while the existing platform stays live. For each phase, list owner, dependency, risk, test, customer effect, success measure, and rollback trigger.

Pass: The plan reduces risk step by step and can be executed by teams rather than only drawn by an architect.

Interview challenge: “A critical downstream team cannot migrate on your schedule. What do you do?”

Interview phrasing

“I would move one capability at a time. Each phase would have compatibility checks, reconciliation, and a rollback condition. I would retire the old path after its consumers and data are accounted for.”

Keep outside this session: A hypothetical full rewrite without constraints.

E02Enterprise architecture, governance, and roadmap alignment

Prerequisites: F01, F02, and E01.

Prepare:

  • Business, data, application, and technical architecture.
  • Platform blueprints and roadmap alignment.
  • Decision rights, reviews, and exceptions.
  • Build-versus-buy, technical debt, and sequencing.

Practice: Create a 12–18 month capability roadmap and a lightweight design-review checklist for the running case. Present a recommendation to a fictional product and technology steering group with alternatives, cost/risk, dependencies, and decision requests.

Pass: Your governance mechanism catches material risk without becoming an approval bottleneck, and the roadmap connects technical work to business outcomes.

Interview challenge: “Two product teams want exceptions to the platform API standard. When would you allow them?”

Interview phrasing

“I would connect each roadmap item to a business outcome. Standards would address shared risks and integration needs. An exception would have a clear reason, owner, and review date.”

A01AI-assisted architecture with verification and controls

Prerequisites: F02, T03, and T06.

Prepare:

  • AI help for requirements, reviews, and documentation.
  • Validation, confidentiality, and traceability.
  • Human decision ownership and design risk.
  • Evaluation and measuring team benefit.

Practice: Give an AI assistant a fictional architecture brief. Keep a finding log with accepted, rejected, and unverified suggestions; show how each accepted suggestion was checked. Propose a team workflow and a measure of its effect on review quality or cycle time.

Interview challenge: “An AI tool recommends an architecture change that appears elegant but conflicts with a security constraint. What is your process?”

“I would check the AI suggestion against the requirement and security constraint. I would verify the evidence before adopting it. I would record accepted, rejected, and uncertain findings for team review.”

Mock scoring rubric

Rate each dimension from 1 to 5. 1 = cannot yet explain; 3 = plausible but incomplete or weak under challenge; 5 = precise, evidence-based, and adaptable. For the final mocks, aim for at least 4 in every dimension twice.

Dimension What to listen for
Business framing User and business outcome before technology
Requirements Key unknowns, constraints, and ranked quality attributes
Technical depth Correct mechanism, data ownership, and failure behavior
Trade-offs Real alternatives, costs, decision, and revisit condition
Security and reliability Specific threats, controls, SLOs, and recovery paths
Delivery Migration, ownership, tests, rollout, and measurable result
Leadership Influence, governance, mentoring, and accountability
Communication Clear reasoning and short answers. Accent and native-like fluency are not scored
