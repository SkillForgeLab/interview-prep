Why must equals and hashCode agree or why must you override both equals and hashCode?

30–60 sec
30–60 second answer

equals() defines whether two Java objects are logically the same, while hashCode() helps hash-based collections locate them. The contract says that if two objects are equal, their hash codes must also be equal. The reverse is not true: different objects can share a hash code, which is called a collision. HashMap and HashSet first use the hash to narrow the search, then use equals() to confirm a match. If I override equals() but keep an incompatible hashCode(), two logically equal objects may end up in different buckets. That can cause failed lookups or duplicate entries in a set. I therefore implement both using the same stable equality fields.

Follow-up What if two unequal objects have the same hash code?

That is allowed. A collision means the collection must compare candidate entries with equals() to tell them apart. It can reduce performance, but does not by itself break correctness. A changing hash code is a different problem: if an object is already a key in a HashMap, changing a field used by equals() and hashCode() may make it unreachable via normal lookup. Prefer immutable keys, and make sure equality is reflexive, symmetric, transitive and consistent. An object's hash is not required to stay the same between separate JVM executions.

Small example Short illustration to help recall 
record Person(String name) {} // Generates consistent equals and hashCode

Set<Person> people = new HashSet<>();
people.add(new Person("Alice"));
people.add(new Person("Alice"));
System.out.println(people.size()); // 1

Both records represent the same name, so the set keeps one entry. Remember: equal ⇒ same hash; same hash ⇏ equal.

What breaks if you override only equals()?

Correct implementation from your notes

import java.util.Objects;

class Person {
    String name;

    Person(String name) { this.name = name; }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof Person other)) return false;
        return Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name);
    }
}

Person p1 = new Person("Alice");
Person p2 = new Person("Alice");
System.out.println(p1.equals(p2)); // true
System.out.println(p1.hashCode() == p2.hashCode()); // true

Set<Person> people = new HashSet<>();
people.add(p1);
people.add(p2);
System.out.println(people.size()); // 1

Lookup flow

hashCode() -> candidate bucket -> equals() -> actual matching entry

The contract between equals() and hashCode()

If two objects are equal according to equals(), they must have the same hashCode().

The reverse is not required: Two objects can have the same hash code but still be unequal. This is called a hash collision.

a.equals(b) == true
    => a.hashCode() == b.hashCode()

Hash-based collections like HashMap and HashSet rely on both methods to find and identify objects correctly.

While equals() defines logical equality, hashCode() helps hash-based collections locate objects efficiently.

Their contract ensures that logically equal objects can be found in the same bucket and correctly identified by equals().

Why is volatile count++ unsafe?

30–60 sec
30–60 second answer

volatile gives Java threads visibility and memory-ordering guarantees, but it does not turn a compound operation into one atomic action. count++ is really three steps: read the current value, add one, and write the result. Two threads can both read five, both calculate six, and both write six. One increment is lost, even though the field is volatile. To implement a shared counter safely, I would use AtomicInteger.incrementAndGet() or protect the increment with synchronized. volatile is useful for a simple state flag that one thread writes and other threads read, but it is not enough for a read-modify-write operation.

Follow-up When would you choose `AtomicInteger` versus `synchronized`?

Choose AtomicInteger for a single atomic numeric variable, including increments and compare-and-set. Use synchronized or another lock when several fields must change together and the whole invariant needs protection. For a highly contended statistics counter, LongAdder can offer better throughput, but sum() is not an atomic snapshot under concurrent updates. A shutdown flag is different: volatile boolean shutdown is suitable when workers only need to see its latest written state. Do not use final for a field you intend to increment or change.

Small example Short illustration to help recall 
AtomicInteger count = new AtomicInteger();

// Two threads each call this 1,000 times:
count.incrementAndGet();
// After both threads complete, count.get() is 2,000.

Remember: visibility is not atomicity.

Interview response: volatile guarantees visibility, not atomicity.

Since count++ is a read-modify-write operation, multiple threads can overwrite each other's updates.

Use AtomicInteger or synchronization when you need a correct shared counter.

Explanation:

Consider this Java code:

private final int count = 0;

// Called by multiple threads
count++;

Although count++ looks like one operation, it actually involves three steps:

  1. Read the current value of count.
  2. Increment the value by one.
  3. Write the new value back to count.

These steps are not atomic.

In Java, volatile provides two important guarantees:

  • Visibility: When one thread writes a new value to a volatile variable, other threads can observe that write.
  • Ordering: It establishes memory-ordering guarantees around volatile reads and writes.

However, it does not make compound operations such as count++ atomic.

Think of it this way:

  • volatile makes individual reads and writes visible.
  • synchronized or atomic classes can make the entire increment operation safe.

How to fix it?

Option A: Use AtomicInteger (usually the simplest choice)


import java.util.concurrent.atomic.AtomicInteger;

private final AtomicInteger count = new AtomicInteger(0);

public void increment() {
    count.incrementAndGet();
}

incrementAndGet() performs the increment atomically, so concurrent updates are not lost.

Option B: Use synchronized


private int count = 0;

public synchronized void increment() {
    count++;
}

Only one thread at a time can execute this synchronized method on the same object, preventing concurrent increments from interfering.

Option C: Use volatile alone

When does ConcurrentHashMap still need higher-level coordination?

30–60 sec
30–60 second answer

ConcurrentHashMap makes its individual map operations thread-safe, and methods such as putIfAbsent() and computeIfAbsent() give atomic operations for a mapping. But that does not mean an entire business workflow is atomic. I still need higher-level coordination when correctness depends on multiple map calls, multiple keys, external state, or a consistent view of the whole map. For example, checking containsKey() and then calling put() leaves a race between those calls. I would replace that with putIfAbsent() or computeIfAbsent(). For a transfer between two account balances, I would use a suitable lock or a database transaction so both changes succeed or fail together.

Follow-up Why doesn't `computeIfAbsent()` solve every race?

It makes the computation and insertion atomic for the relevant map key; it is not a transaction spanning several keys or a database. Its mapping function should be short, and it must not modify that same map while computing. The function can also fail, leaving the mapping absent. If initializing a resource also writes to a database and publishes an event, I need an explicit workflow: for example, a state machine, coordinated transaction, or reliable outbox. Bulk traversal of a concurrently changing map also does not guarantee one globally consistent snapshot.

Small example Short illustration to help recall 
// Race-prone:
if (!map.containsKey("job-1")) map.put("job-1", new Job());

// Atomic insertion of a single key:
map.computeIfAbsent("job-1", key -> new Job());

Remember: thread-safe operations do not imply a thread-safe sequence.

Additional details Organized explanations + complete original notes

Map safety versus workflow safety

ConcurrentHashMap protects its internal map operations. It cannot make an unrelated sequence or business invariant atomic.

All four situations from your notes

  1. Check then act: containsKey() followed by put() has a gap where another thread can act. Use putIfAbsent() or computeIfAbsent() as appropriate.
  2. Multiple keys: A bank transfer updates two account balances. Each map operation can be safe while the overall transfer is inconsistent; use coordination or a transaction.
  3. Global invariant: Checking total allocation and adding to map and totalAllocated must be one coordinated operation to enforce a capacity limit of 100.
  4. Multi-step lifecycle: Initializing a service, registering it and publishing status needs a lock, Future, or explicit state machine when it must happen once. 
// Check-then-act race:

    map.put(key, createValue());
}

// Atomic computation for one mapping:
map.computeIfAbsent(key, k -> createValue());

Keep computeIfAbsent() mapping functions short; do not modify other mappings in the same map from the function. Neither this method nor the map itself coordinates external state.

What is the difference between thenApply and thenCompose?

30–60 sec
30–60 second answer

Both methods continue a CompletableFuture after an earlier stage produces a result. I use thenApply() when I want to transform a value into another ordinary value. For example, take a user's name and convert it to uppercase. I use thenCompose() when the next function starts or returns another asynchronous operation. It flattens the nested future so the result is one CompletableFuture rather than a future containing another future. A simple rule is: thenApply is like map; thenCompose is like flatMap. Neither method automatically makes blocking code non-blocking; I still need to consider which thread executes the callback.

Follow-up When would you use `thenCombine()` instead?

Use thenCompose() when the second operation depends on the result of the first, such as fetching an account after fetching the account ID. Use thenCombine() when two futures can be initiated independently and you want to combine their results once both complete, such as retrieving a price and an exchange rate in parallel. Also distinguish thenApply() from thenApplyAsync(): the latter schedules the function with an asynchronous execution facility, or a supplied executor. An Async suffix is not a license to run blocking work on an inappropriate executor.

Small example Short illustration to help recall 
CompletableFuture<String> name = CompletableFuture.completedFuture("Sam");

CompletableFuture<String> upper = name.thenApply(String::toUpperCase);

CompletableFuture<User> user = name.thenCompose(this::fetchUserAsync);
// fetchUserAsync(String) returns CompletableFuture<User>

Remember: thenApply transforms; thenCompose chains and flattens.

Additional details Organized explanations + complete original notes

Two continuation methods

  • thenApply() accepts the preceding value and returns a new ordinary value. Its result is a CompletableFuture<T>.
  • thenCompose() accepts the preceding value and returns another CompletionStage<T>; composition flattens the nested future.

Original thenApply() example, formatted

CompletableFuture<String> future =
    CompletableFuture.supplyAsync(() -> "Hello")
        .thenApply(s -> s + " World");

System.out.println(future.join()); // Hello World

Follow-on async operation

CompletableFuture<User> user =
    fetchUserIdAsync().thenCompose(id -> fetchUserAsync(id));

Choose the method based on what the continuation returns, not just whether it runs after another stage. The earlier draft included the first example and the flattening rule; the second code example is an added illustration.

Why can JDBC block a Vert.x event loop?

30–60 sec
30–60 second answer

Vert.x event loops are designed to handle many events with a small number of threads. They work well only when handlers return quickly. Traditional JDBC is a blocking API: executing a query or waiting for a connection can hold the calling thread until the operation finishes. If I call JDBC directly in an event-loop handler, that loop cannot process other requests or timers while it waits. Even a normal database delay can therefore hurt many unrelated requests. I would run blocking JDBC on a worker thread with executeBlocking(), or preferably use an asynchronous Vert.x SQL client where appropriate. I would also avoid calling join() or get() from the event-loop thread.

Follow-up Does wrapping JDBC in `CompletableFuture.supplyAsync()` fix the problem?

Only if the JDBC work actually runs on a suitable executor and the event loop never blocks waiting for it. Calling supplyAsync(...).join() from the event loop still blocks that loop. Using the common pool for a large volume of blocking database work can also exhaust the pool's useful capacity, so executor and connection-pool sizing matter. Vert.x executeBlocking() places blocking work on a worker pool and returns a future; callbacks can continue asynchronously. A reactive SQL client avoids occupying a thread while the request waits for a database response, but the database query can still be slow.

Small example Short illustration to help recall 
vertx.executeBlocking(() -> jdbcQuery())
    .onSuccess(result -> request.response().end(result))
    .onFailure(err -> request.response().setStatusCode(500).end());

Remember: moving work off-loop helps only if you do not wait on-loop.

Additional details Organized explanations + complete original notes

Why it hurts an event loop

A Vert.x event loop serves many connections using relatively few threads. It needs each handler to return quickly. JDBC waits synchronously for a connection or query to finish; delays can come from the pool, locks, network latency, and the database query itself.

Option A: Offload blocking JDBC

vertx.executeBlocking(() -> jdbcQuery())
    .onSuccess(result -> {
        // Continue on the original Vert.x context.
        request.response().end(result);
    })
    .onFailure(err -> request.response().setStatusCode(500).end());

Vert.x runs the blocking call on a worker thread and completes the returned future on the original context.

Option B: Use a reactive SQL client

pool.preparedQuery("SELECT name FROM users WHERE id = ?")
    .execute(Tuple.of(userId))
    .onSuccess(rows -> {
        // Continue without waiting synchronously on the event loop.
    });

Trap: asynchronous work followed by a blocking wait

CompletableFuture.supplyAsync(() -> jdbcQuery()).join();

Although jdbcQuery() may execute on another thread, join() blocks the thread calling it. If that is an event loop, the problem remains. Compose callbacks instead of waiting.

Consequences and diagnosis

  • Latency: unrelated requests wait while the loop is blocked.
  • Throughput: fewer requests per second are handled.
  • Scalability: widespread blocked event loops can make the service unresponsive.
  • Diagnostic clue: Vert.x can log blocked-thread warnings, such as vertx-eventloop-thread-3 has been blocked.

How the Vert.x event loop works

A Vert.x event loop typically handles events for many connections on a small number of threads. As such, they depend on handlers returning quickly so it can continue processing other requests, timers, and I/O events.

Traditional JDBC operations are synchronous (blocking). So, even if the database is healthy, network latency, connection-pool waits, locks, or a slow query can keep the thread blocked.

The problem isn't necessarily the database being slow. It's that the event loop is waiting synchronously.

How to fix it?

Option A: Use executeBlocking ()

vertx.executeBlocking(() -> {
    return jdbcQuery(); // Runs on a worker thread
}).onSuccess(result -> {
    // Handle result on the original Vert.x context
    request.response().end(result);
}).onFailure(err -> {
    request.response().setStatusCode(500).end();
});

This keeps the JDBC call off the event loop. Vert.x runs the blocking callable in its worker pool and completes the returned future on the original context.

Option B: Use a reactive database client

For a more naturally non-blocking architecture, use an appropriate Vert.x reactive database client, such as a reactive SQL client supported for your database.

pool.preparedQuery("SELECT name FROM users WHERE id = ?")
    .execute(Tuple.of(userId))
    .onSuccess(rows -> {
        // Handle results without blocking the event loop
    });

Here, the database operation is asynchronous: the event loop can process other events while waiting for the database response.

Does wrapping JDBC in a CompletableFuture solve it?

Not by itself.

This is still dangerous when called from a Vert.x event loop:

CompletableFuture.supplyAsync(() -> jdbcQuery())
   .join();

Although supplyAsync() usually runs the JDBC operation on a different thread, join() blocks the calling thread while waiting for the result. If that calling thread is an event loop, you still have the same problem.

Instead, compose asynchronous stages without blocking: This avoids blocking the event loop, provided the callback itself doesn't perform blocking work.

vertx.executeBlocking(() -> jdbcQuery())
.onSuccess(result -> {
// Continue asynchronously
});

Why does this matter for performance?

Latency: Other requests on the blocked event loop wait longer.

Throughput: Fewer requests can be processed per second.

Scalability: If all event loops become blocked, the entire Vert.x instance can become unresponsive.

Diagnostics: Vert.x can log warnings such as vertx-eventloop-thread-3 has been blocked

What does Spring Boot add to Spring?

30–60 sec
30–60 second answer

Spring is the underlying framework for dependency injection, application components, web development and other infrastructure. Spring Boot builds on it to reduce setup and provide a simpler way to run applications. Its main additions are auto-configuration, starter dependencies, embedded server support, externalized configuration, and production features through Actuator. For example, adding a web starter lets Boot configure much of a typical web application based on the dependencies present, while allowing me to override defaults. I can often package and run the application directly as an executable JAR. Boot does not replace Spring; it makes common Spring application setups faster and more consistent.

Follow-up How does auto-configuration know what to create?

Boot evaluates conditions, including which classes and beans exist and which configuration properties are set. If relevant libraries are available and I have not supplied my own bean, Boot may configure a default. If I define a compatible explicit bean, the auto-configuration can back off. @SpringBootApplication enables key application setup, including auto-configuration and component scanning. Starter dependencies help assemble compatible libraries; they are not themselves the runtime mechanism that creates every bean. Actuator exposes operational features such as health and metrics, subject to dependencies and endpoint exposure settings.

Small example Short illustration to help recall 
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);
    }
}

With appropriate web dependencies, Boot can set up an embedded web server and the surrounding web infrastructure.

Why might @Transactional not take effect?

30–60 sec
30–60 second answer

The first thing I check is whether the method call went through a Spring-managed transaction proxy. In Spring's default proxy mode, a method calling another annotated method on the same object bypasses the proxy, so the inner annotation does not start a new transactional boundary. I also check that Spring created the bean, the method can be intercepted, and the correct transaction manager is configured. Sometimes the transaction exists but the result looks wrong because of rollback rules: by default, Spring rolls back for unchecked exceptions and errors, not ordinary checked exceptions. Finally, asynchronous work or operations on unrelated database connections may be outside the transaction.

Follow-up How would you debug a transaction that unexpectedly committed?

I would check whether the method was invoked through a proxy and whether the transaction was active on that thread. Then I would inspect the exception: was it checked, caught and swallowed, or deliberately configured not to roll back? For a checked exception, I can use @Transactional(rollbackFor = Exception.class) when that behavior is required. I would also verify propagation settings such as REQUIRED versus REQUIRES_NEW, the chosen transaction manager, and whether the database work uses an enlisted connection. These are separate failure modes; an annotation alone cannot make unrelated external services part of one transaction.

Small example Short illustration to help recall 
@Service
class OrderService {
    void placeOrder() { save(); }     // Self-call bypasses proxy advice

    @Transactional
    public void save() { /* persist order */ }
}

Move save() to an injected Spring-managed OrderWriter service and call it through that bean, or design the public transactional boundary on placeOrder() itself.

    • Static methods: Are not intercepted by standard Spring transaction proxies.

  1. Transaction propagation changes the behavior

Propagation settings can cause a method to join an existing transaction or start a separate one.

  • REQUIRED — joins an existing transaction or creates one.

  • REQUIRES_NEW — suspends an existing transaction and starts a new one.

  • SUPPORTS — participates in a transaction if one exists, but does not require one.

  • NOT_SUPPORTED — executes without a transaction, suspending an existing one if applicable.

  • NEVER — requires that no transaction exists.

For example:


@Transactional(propagation = Propagation.NOT_SUPPORTED)

}

Common reasons include:

  • The operation uses a different database connection or data source.
  • A database operation is performed through a resource not enlisted in the transaction.

  • The code commits manually or uses autocommit outside Spring's transaction management.
  • The code reads from a replica or another connection and observes different state.
  • The transaction commits before an asynchronous operation executes.

  • jakarta.transaction.Transactional — Jakarta Transactions annotation, supported in appropriate Spring configurations.

How do you detect and fix N+1 queries?

30–60 sec
30–60 second answer

N+1 is a database access pattern where I load N parent records with one query, and then issue an additional query for each parent's related data. For example, loading 100 orders and lazily reading each order's customer can result in 101 queries. To detect it, I enable SQL logging or query-count metrics and observe how the query count grows when the number of returned records grows. To fix it, I choose a fetching strategy that matches the use case: a join fetch or entity graph for the needed relations, batch fetching for multiple lazy associations, or a projection that selects only required columns. I verify the improvement with a realistic dataset.

Follow-up Why not make every relationship eager?

Eager loading can over-fetch unnecessary data and may still result in extra SQL selects, depending on the query and ORM fetching strategy. Fetch-joining several to-many associations can multiply rows and complicate pagination. I prefer explicit fetching for a particular read path instead of making the whole model eager. For a list API, a DTO projection is often efficient because it avoids building a large object graph. I would compare SQL count, rows returned, total latency and memory, not just the number of queries. The correct solution depends on whether the relationship is to-one, to-many, paginated, or used by multiple endpoints.

Small example Short illustration to help recall 
// JPQL: load orders and their customer in one SQL join
@Query("select o from Order o join fetch o.customer")
List<Order> findOrdersWithCustomer();

For a to-one relation this can avoid per-order lazy loads. Test carefully before fetch-joining to-many collections with pagination.

How do you prevent lost updates?

30–60 sec
30–60 second answer

A lost update occurs when two requests read the same value and later one write overwrites the other request's change. The common case is two users editing the same record based on an old version. My default choice for ordinary JPA entity updates is optimistic locking with a @Version column. The database update checks that the version has not changed; if another transaction already updated the row, the later update fails with a conflict instead of silently overwriting data. I can then ask the caller to reload or safely retry. For counters, I prefer an atomic database update, and for high-contention workflows I consider row locks.

Follow-up Optimistic or pessimistic locking — which would you choose?

Optimistic locking is a good starting point when conflicts are infrequent, because reads do not require a long-held exclusive lock. A conflict becomes visible at update or commit and the application must decide whether a retry is safe. Pessimistic locking, such as SELECT ... FOR UPDATE, can be appropriate when a short transaction must serialize access to a row, but it increases waiting and deadlock risk. For simple increments, a single SQL statement is often better than read-then-write. I also check transaction boundaries and isolation: simply putting several requests in transactions does not automatically prevent every lost-update scenario.

Small example Short illustration to help recall 
@Entity
class Product {
    @Id Long id;
    @Version Long version;
    int stock;
}

If two transactions loaded version 3, the first can update it to version 4; the second then gets an optimistic-lock conflict instead of silently replacing the first update.

Why can a LEFT JOIN unexpectedly remove unmatched rows?

30–60 sec
30–60 second answer

A LEFT JOIN normally returns every row from the left table, even when there is no matching row on the right. For an unmatched row, columns from the right table become NULL. The surprise comes when I add a condition on the right table in the WHERE clause, such as WHERE payment.status = 'PAID'. For unmatched rows, that comparison is not true, so the WHERE clause removes them. The query then behaves like an inner join for that condition. If I want all left-side rows but only qualifying matches from the right table, I put the right-side filter in the ON clause instead.

Follow-up When is a right-table condition in `WHERE` correct?

It is correct when the business question intentionally wants only rows that have a qualifying match. For example, "customers who have a paid order" legitimately excludes customers without a paid order. But "all customers, showing paid orders if any" requires a LEFT JOIN with the paid filter in ON. There is another useful pattern: LEFT JOIN ... WHERE right.id IS NULL to find left-side rows with no matching right-side record. I always translate the SQL back into the expected business result and test it with one matched row and one unmatched row.

Small example Short illustration to help recall 
-- Keeps customers even if they have no PAID order:
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status = 'PAID';

Remember: ON affects matching; WHERE filters the result after the join.

Why unmatched rows disappear

LEFT JOIN preserves all left-table rows initially. When no right-side record matches, that side's columns are NULL. A right-table condition in WHERE, such as o.status = 'PAID', removes those null-extended rows.

Compare the two queries

-- Keeps only customers with a paid order:
SELECT c.id, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'PAID';

-- Keeps all customers; attaches paid orders when available:

FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status = 'PAID';

How do you invalidate Redis data safely enough for the use case?

30–60 sec
30–60 second answer

I start with the business requirement: how stale can the data be, and what happens if it is wrong? For ordinary read-heavy data, I often use cache-aside: read from Redis first, load from the database on a miss, and store the value with a TTL. When a write succeeds in the database, I invalidate the specific Redis key so the next reader reloads it. The TTL limits how long a forgotten or missed invalidation can persist. I also plan for races where a concurrent reader loads an old value and repopulates the cache after invalidation. For sensitive data, such as authorization or balances, I use stronger consistency controls or bypass the cache.

Follow-up What is the invalidation race and how do you prevent it?

Imagine reader A sees a cache miss and starts loading version 1 from the database. Writer B commits version 2 and deletes the cache key. Then A finishes late and writes version 1 back into Redis. The key is stale even though deletion happened after the database write. Possible controls include a versioned cache key, storing and checking a record version, serializing loads and writes for the key, or using change events with carefully designed ordering. Exact choice depends on tolerated staleness. For hot keys, a short-lived request-coalescing mechanism can reduce stampedes. A TTL is a safety net, not proof of immediate consistency.

Small example Short illustration to help recall 
GET product:42 -> cache miss
DB SELECT product 42 -> price 20
SET product:42 (value=20, TTL=60s)

On successful price update:
DB UPDATE product 42 -> price 25
DEL product:42

This is the basic cache-aside flow; production code must address concurrent repopulation.

What must you validate in a JWT besides its signature?

30–60 sec
30–60 second answer

A valid JWT signature only proves that the token was signed with an accepted key and has not been modified. It does not automatically mean the token should be accepted by my API. I also validate its expected issuer, audience, and time-based claims such as expiration and not-before. I restrict the allowed signing algorithms, select keys from a trusted source, and confirm the token type and intended use, such as access token versus ID token. Then I validate application-specific identity, scopes or roles and resource permissions. If my system supports revocation, I also check whether the token or session has been revoked.

Follow-up Why is an audience check important?

An identity provider might issue tokens for several APIs. A token that has a valid signature could still be intended for a different service. Checking aud prevents another application's token from being accepted by mine. Similarly, iss binds the token to a trusted issuer, and the signing key must belong to that issuer. I must not let the token header arbitrarily choose an algorithm or an untrusted remote key source. exp and nbf are time validity checks; small clock-skew allowances may be configured. The claims identify and constrain the caller, but authorization must still be enforced at the requested resource.

{
  "iss": "https://auth.example.test",
  "aud": "orders-api",
  "sub": "user-123",
  "exp": 1900000000
}

The orders-api must reject this token if its issuer is untrusted, it is expired, or it is not an intended audience—even if its signature verifies.

How do you prevent cross-tenant access?

30–60 sec
30–60 second answer

In a multi-tenant system, I apply defense in depth. I first authenticate the user, then verify that they belong to the tenant they want to access and have permission for the requested resource. The backend creates a trusted tenant context; it must not assume that a tenant ID sent in a header or URL is authorized. Every data-access operation must enforce that scope. In a shared PostgreSQL database, I would use tenant-filtered queries backed by row-level security where practical. I would also namespace cache keys and file paths by tenant, carry tenant context into background jobs, and run automated negative tests proving tenant A cannot access tenant B's data.

Follow-up Is `WHERE tenant_id = ?` enough?

It is necessary in many designs, but not enough on its own. A developer could forget the predicate, a background job could reuse the wrong tenant context, or a cache key could omit the tenant. PostgreSQL row-level security adds a database enforcement layer. When using a transaction-scoped setting such as app.tenant_id, set it from an already verified backend identity inside the transaction and use a database role that cannot bypass RLS. Superusers and BYPASSRLS roles bypass those policies; table owners normally bypass them unless FORCE ROW LEVEL SECURITY applies. I would test reads, writes, files, caches and pooled connections.

Small example Short illustration to help recall 
-- tenant_id must come from trusted, authorized server context:
SELECT id, title
FROM documents
WHERE id = :document_id
  AND tenant_id = :verified_tenant_id;

Even if a user guesses another document ID, the query does not return data outside the verified tenant.

What does a payment timeout actually tell you?

30–60 sec
30–60 second answer

A payment timeout tells me that my system did not receive a definitive response within the allowed time. It does not prove that the charge failed. The payment provider may have received and completed the request, but the response could have been delayed or lost. Therefore, blindly retrying with a new request can create a duplicate charge. I treat the payment state as unknown or pending reconciliation, not automatically failed. I use an idempotency key for safely retrying the same logical operation, check the payment status using the provider's authoritative API or supported webhooks, and record the final state reliably before telling the customer the outcome.

Follow-up What would a reliable payment flow look like?

Before sending a create or capture request, persist an internal payment attempt with a unique identifier and idempotency key. Use the same key for retries of that same operation, following the provider's documented retention and retry rules. On timeout, do not initiate a fresh independent charge. Query the existing payment, receive provider webhook events with verified authenticity, deduplicate event handling and reconcile if the response remains uncertain. Model states such as PENDING, SUCCEEDED and FAILED, and define when the order may be fulfilled. Different gateways have different semantics, so I would follow the selected provider's API rather than assume all timeouts behave identically.
